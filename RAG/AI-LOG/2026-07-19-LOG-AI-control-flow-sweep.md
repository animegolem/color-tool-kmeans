# 2026-07-19 whole-app control-flow sweep

## Scope and method

Repository-wide audit of shipping Svelte/Tauri control flow, Rust command and cache paths, duplicated logic, and one-off helpers that should be unified. Bench binaries are inspected only for shared-production coupling; planned notebook/live-playback work is not classified as a shipping defect unless current production code is affected.

Candidate findings enter the agent sections below. Root review assigns a stable `SWEEP-NNN` ID only after checking callers, existing tickets, tests, and reproducibility. Rejected and merged leads remain recorded so the final count is honest.

## Register rules

- Severity: P1 data loss/security/crash on ordinary use; P2 major incorrect result or persistent broken state; P3 bounded functional/reliability defect; P4 maintainability, duplication, or misleading behavior.
- Evidence must include an exact path and line or symbol, the triggering sequence, and the observable consequence.
- Distinguish a confirmed defect from a refactor opportunity.
- Cross-reference old `AUD-*` findings and active tickets; do not recount remediated or planned behavior.
- Each agent edits only its named section.

## Frontend async and lifecycle candidates

### FE-01 — Debounced raw-video selection can override a newer still selection (confirmed defect, P2)

- **Classification / evidence:** bug. `stores/image.ts:346-355` keeps the raw-video debounce in module-global `_videoSwitchTimer`, but `setFile()` (`161-198`), `switchToFile()` (`302-321`), `clearActiveSelection()` (`323-337`), and `clearFile()` (`364-384`) neither cancel that timer nor clear an already-published `pendingVideoSwitch`. The pending event is consumed by `services/view-subscriptions.ts:12-23` and immediately loads the video in Home/Values.
- **Trigger / consequence:** click raw video A in the media bucket, then click or ingest still B within 150 ms. B becomes active synchronously; A's older timer then publishes and the mounted view loads A, so the last user selection loses and the app unexpectedly returns to video mode. The same sticky event can survive a view without a subscriber and replay on a later Home/Values mount.
- **Validation performed:** deterministic timer/store trace against the exact callbacks: `switchToVideo(A) -> switchToFile(B) -> +150 ms -> pendingVideoSwitch(A) -> loadVideoSelection(A)`. There is no intervening guard for the current `activeImageId` or a selection epoch.
- **Old overlap:** new gap, not one of AUD-001/002; AI-IMP-162 orders probes/decodes after a video request has started but does not order a pending video request against a later still selection.
- **Smallest fix / independence:** add one `cancelPendingVideoSwitch()` store helper that clears both timer and event, and invoke it from every non-video activation/clear path. Minimal files: `stores/image.ts`, `services/view-subscriptions.ts` only if event semantics change, and `views/__tests__/audit-control-flow-races.spec.ts`. **Semantically independent, though a central selection-generation fix for FE-02 could absorb it.**
- **Implementation (SWEEP-013):** completed. Added canonical `cancelPendingVideoSwitch()` ownership cleanup in `stores/image.ts`; it clears both `_videoSwitchTimer` and an already-published `pendingVideoSwitch`. `setFile()`, valid `switchToFile()`, `clearActiveSelection()`, and `clearFile()` now invoke it before non-video activation/clear, while `switchToVideo()` also uses it so a replacement video request cannot leave an older published event live. Added focused fake-timer store coverage in `image-video-switch-lifecycle.spec.ts` for a newer `setFile`, published-event cancellation before a later subscriber, and both active/full clear paths.
- **Implementation gates:** focused SWEEP-013 Vitest `3 passed`; combined image/video-switch, Colors lifecycle, and Values lifecycle suites `7 passed` across 3 files; `npm run check` passed with `0 errors` and the 2 accepted AUD-020 accessibility warnings; `npm run lint` passed; targeted Prettier check and `git diff --check` passed.

### FE-02 — View-owned video completions remain authoritative after unmount (confirmed defect, P2)

- **Classification / evidence:** bug. Home cleanup cancels only its color runner (`HomeView.svelte:449-465`); `createVideoController()` exposes no dispose operation (`home/video-controller.svelte.ts:788-846`). Its frame completion still calls `setFile()`, schedules analysis, pushes `videoState`, and caches (`313-358`), while its probe completion can also generate work and push state (`440-464`). Values destroys its scrubber but not its ingestion controller (`ValuesView.svelte:177-205`); a pending Values probe therefore retains its generation and can call `setVideoState()` after unmount (`values/file-ingestion-values.svelte.ts:28-75,146-152`).
- **Trigger / consequence:** start frame extraction/probe for A, navigate to the other view, and select B before A resolves. The unmounted A controller still passes its local path/token guard and overwrites the new view's global selection with A; it can also start a Home analysis runner after that runner was already canceled on destroy. This is wrong-video attribution across the mount boundary.
- **Validation performed:** executable expected-failure repro with a deferred Home frame: start A, advance through the 250 ms debounce, set global `videoState` to B (the new view), resolve A, and observe final state revert to A. The temporary repro passed under `it.fails` and was removed after validation. Values has the same source-proven lifetime hole for a deferred probe.
- **Old overlap:** adjacent to AUD-001/002/007 and AI-IMP-162, but those regressions cover ordering while the owning controller remains mounted. Deferred AI-IMP-124 would centralize frame reuse but does not currently specify unmount ownership.
- **Smallest fix / independence:** either (a) add `dispose()` generation invalidation to both video controllers and call it from view cleanup, with Values acquiring a frame when the store timestamp differs from the selected frame, or (b) use a store-level media-selection generation checked by every completion. Minimal files: `HomeView.svelte`, `ValuesView.svelte`, both video controller/ingestion modules, optionally `stores/video.ts`, and `audit-control-flow-races.spec.ts`. **Coupled to FE-01 if solved with a selection generation; coordinate with deferred AI-IMP-124.**
- **Implementation (SWEEP-023):** completed with owner-local disposal rather than a new global selection generation. Home's `dispose()` permanently revokes the controller, invalidates/clears decode and source-load timers/queues, and makes frame/probe/strip completions plus state/cache publishing stale; `HomeView` invokes it before unsubscription during cleanup. Values ingestion now has a disposal flag plus generation invalidation for probes and post-dialog/batch work, and `ValuesView` disposes both ingestion and its existing frame scrubber before other cleanup. This composes with SWEEP-013: stale video-frame `setFile()` already cannot cancel a newer raw-video debounce, and now an unmounted Home frame cannot reach `setFile()` at all.
- **Implementation regressions:** extended `home/video-controller-cache-reset.spec.ts` with a deferred frame that begins under owner A, disposes, transfers selection to B, then resolves without `setFile` or state publication. Added `values/file-ingestion-values-disposal.spec.ts` with the parallel deferred probe sequence against the real `videoState` store. Existing cached restore coverage remains green (SWEEP-003 and AUD-008).
- **Implementation gates:** focused owner/cached tests `3 passed` across 2 files; full targeted control-flow set `27 passed` across 5 files, including all 19 `audit-control-flow-races` cases and SWEEP-013; `npm run check` passed with `0 errors` and the 2 accepted AUD-020 accessibility warnings; `npm run lint` passed; targeted Prettier check and `git diff --check` passed.

### FE-03 — A cached video's pending seek leaks into the next fresh video (confirmed defect, P3)

- **Classification / evidence:** bug. `resetVideoState()` does not reset `_pendingSeekTime` (`home/video-controller.svelte.ts:120-163`). Cached load A assigns it from A's current time (`494-531`), while the uncached load path for B does not assign it at all (`534-556`). B's metadata handler then consumes the stale A value and seeks B to it (`622-639`). `_restoringFromSessionCache` is likewise not normalized on reset, but the seek has the direct observable failure.
- **Trigger / consequence:** activate cached A at 7 s and switch to uncached B before A's `<video>` metadata event. When B metadata arrives, B jumps to 7 s and its first extracted/analyzed frame comes from the wrong starting timestamp.
- **Validation performed:** executable expected-failure controller repro with a cached A at 7 s, immediate fresh B load, and a fake B video metadata event. Both `controller.videoCurrentTime` and the element's `currentTime` become 7 instead of 0. Temporary repro removed after validation.
- **Old overlap:** same identity family as AUD-001/002, but neither audit case covered DOM seek carryover between two Home loads.
- **Smallest fix / independence:** reset `_pendingSeekTime` and `_restoringFromSessionCache` in `resetVideoState()`, then explicitly assign the intended pending seek in every load branch. Minimal files: `home/video-controller.svelte.ts` and `audit-control-flow-races.spec.ts`. **Safely independent; likely the smallest first implementation.**
- **Implementation (SWEEP-003):** completed. `resetVideoState()` now clears both `_pendingSeekTime` and `_restoringFromSessionCache`, so every fresh/cached/session-state branch starts from a normalized restoration boundary and then assigns only its own transient state. Added the focused `home/video-controller-cache-reset.spec.ts` rather than extending the oversized audit suite; its executable regression switches immediately from cached A at 7 s to uncached B and verifies both that B remains at 0 s on metadata and that B's decoded frame takes the normal analysis path instead of the cache-restoration shortcut.
- **Implementation gates:** focused Vitest `1 passed`; `npm run check` passed with `0 errors` and the 2 accepted AUD-020 accessibility warnings; `npm run lint` passed; targeted Prettier write/check passed for both touched TypeScript files; `git diff --check` passed. ### FE-04 — Removing or clearing media does not revoke Values request ownership (confirmed defect, P3)

- **Smallest fix / independence:** route `removeFile()` through `invalidateValueAnalysisForImage()` and add a token-aware `clearAllValueAnalysis()` for `clearFile()`; delete the duplicate key-removal logic in `image.ts`. Minimal files: `stores/value-analysis.ts`, `stores/image.ts`, and `audit-control-flow-races.spec.ts`. **Independent, but land after XC-01 so every caller is token-owned.**

### FE-06 — Batch results have no pinned-source revision identity (confirmed defect, P2)

- **Classification / evidence:** bug. `multi-analysis.ts:51-70` resets only when pinned IDs disappear; replacement of a pinned entry under the same ID does not invalidate `multiAnalysisResult`. Batch compares only serialized pin IDs (`BatchView.svelte:153-176`). Its runner key contains paths/parameters (`batch/batch-runner.svelte.ts:104-127`), but `reanalyze()` ignores the passed paths and analyzes the already-composed `multiCompositePath` (`130-166`). On remount, `BatchView:47-55` seeds the new path key against whatever old result happens to be in the global store.
- **Trigger / consequence:** pin a settled video frame plus another image, analyze Batch, return to Colors/Values and scrub that pinned logical video entry to a new frame (same ID, new frame path), then return to Batch. The old aggregate remains `ready`; remount seeds the dedup key with the new path, and later parameter reanalysis still uses the old composite. The visible pins and aggregate result describe different pixels.
- **Validation performed:** executable expected-failure store repro creates a ready batch result, replaces a pinned logical entry under the same ID/path revision, and expects multi-analysis to reset. Current state remains `ready` with the old result. Temporary repro passed under `it.fails` and was removed. The runner/remount trace proves why the view does not repair it.

- **Smallest fix / independence:** in `multi-analysis.ts`, track the last pinned entry objects/revision signature and reset when a pinned entry is replaced (not merely removed); add a regression covering video-frame replacement and remount. Minimal files: `stores/multi-analysis.ts` plus a new store/batch spec (and `batch-runner.svelte.ts` only if live path changes should automatically recompose). **Independent; does not conflict with the notebook Batch template rebuild.**

### FE-07 — Preference hydration and writes are not ordered (confirmed reliability defect, P3)

- **Classification / evidence:** bug. Startup mounts the app immediately and applies `loadPrefs()` later with no revision guard (`main.ts:53-56,64-70`), while persistence subscriptions are already active (`stores/preferences.ts:74-93,113-146`). Each subscription independently calls read-modify-write `savePrefs()`; that function performs `get -> merge -> set -> save` with no serialization (`stores/prefs.ts:260-288`).
- **Trigger / consequence:** (1) change a Home control before the initial store read resolves: late hydration overwrites the user's newer value and clears/replaces its debounced write. (2) change two different preference stores within one IPC round trip: both saves can read the same old object, then the last `set` overwrites the other partial update. Restart reveals one or both changes lost. Reset can race an already-started save for the same reason.
- **Validation performed:** exact await interleavings were traced against the shipped Tauri `LazyStore`, whose `get`, `set`, and `save` are separate async IPC calls (`node_modules/@tauri-apps/plugin-store/dist-js/index.js:66-72,162-174`). No queue, hydration flag, or compare-and-set exists in app code.
- **Old overlap:** preference persistence predates the July audit and is not covered by EPIC-028. Planned AI-IMP-177 restyles Settings but does not alter persistence logic.
- **Smallest fix / independence:** hydrate before interactive mount (or reject hydration if a local revision changed) and serialize/coalesce preference mutations through one write queue owning the latest full snapshot. Minimal files: `main.ts`, `stores/preferences.ts`, `stores/prefs.ts`, and a new mocked-store ordering spec. **Independent but should be one preference-ordering commit, not two competing fixes.**

During that debounce, `ValuesView.captureFrame()` copies `runner.file.path` (the previous settled frame) while labeling it with the already-updated `scrubber.currentTime` (`ValuesView.svelte:157-164`), and the snapshot button remains enabled because it checks only `scrubber.extracting` (`283-286`). - **Old overlap:** concrete correctness consequence of the deferred Home/Values divergence in AI-IMP-124, but not the structural duplication itself and not covered by AUD-001.

## Rust, Tauri, cache, and process candidates

### RT-01 — Copying a source export onto itself truncates the source to zero bytes (implemented as SWEEP-002, P1)

- **Classification / evidence:** unrecoverable data-loss bug. `tauri-app/src-tauri/src/commands.rs:241-253` passes arbitrary renderer-supplied source/destination paths directly to `std::fs::copy` after creating the destination parent. `bridges/fs.ts:79-97` exposes this through the source-export save dialog and has no same-file check.
- **Trigger / consequence:** export a source image (or a persisted snapshot/composite), choose the original source path as the destination, and accept the platform's replace confirmation. On macOS, `std::fs::copy(path, path)` opens/truncates the destination inode before reading it, returns `Ok(0)`, and the command reports success; the user's original is now an empty file.
- **Validation performed:** the original temporary Rust regression seeded `preserve-me`, executed `std::fs::copy(&path, &path)`, and reproduced `same-path result=Ok(0) bytes=[]`. SWEEP-002 adds permanent unit coverage proving exact same-path and hard-link-alias copies preserve both names' bytes, plus an ordinary overwrite test proving the destination receives the source bytes while the source remains intact.
- **Overlap:** new; AUD-012 / AI-IMP-164 corrected source-export extensions but did not protect source identity. `frame-snapshot.ts` normally copies across roots, so this is specifically the user-selectable export path.
- **Resolution (SWEEP-002):** `copy_file` now delegates to one helper that treats filesystem-identical source/destination handles as a successful no-op. Real copies stream into a uniquely named sibling temporary file, copy source permissions, synchronize the temporary contents, and atomically persist over the destination; a failed copy or persist leaves the prior destination untouched and the temporary file is cleaned up. `same-file` makes identity detection hard-link-aware on supported desktop platforms, while `tempfile` supplies atomic replacement semantics on Unix and Windows. Files: `commands.rs` and direct dependency declarations in `Cargo.toml`. **Safely independent.**

### RT-02 — Concurrent Batch compositions share `batch-grid.png` and can analyze the wrong pins (implemented as SWEEP-019, P2)

- **Classification / evidence:** native file-identity race. `compose_grid.rs:91-101` always saves every request to `<cache>/batch-grid.png`. `batch-runner.svelte.ts:203-263` permits a newer `analyze()` while an older composition is still executing; its token check discards the stale promise only *after* native composition has written. The accepted request then analyzes that shared pathname. `reanalyze()` also reads the same global path at `130-165`.
- **Trigger / consequence:** start slow composition A, then composition B. If B writes/returns and begins `analyze_image`, then stale A finishes and overwrites `batch-grid.png`, B's accepted analysis can read A's pixels while the UI/pins/token all identify B. The returned composite/export path can likewise mutate after acceptance.
- **Validation performed:** the original deterministic source invariant proved all same-cache requests returned one pathname while frontend ownership was checked only after the native write. SWEEP-019 adds a native two-thread regression that simultaneously composes different pixel sets into one cache directory, asserts distinct returned paths, then opens both after both writers finish and verifies each retained path still contains its own pixels. The existing deterministic-output regression continues to prove equal inputs produce byte-identical PNG content despite unique filenames.
- **Overlap:** AI-IMP-133 explicitly chose the stable path under the then-valid assumption that analysis was manual and non-overlapping; the current runner is token-cancellable/debounced. FE-06 concerns stale pinned-source revisions and XC-06 concerns duplicated compute plumbing; neither prevents this writer race.
- **Resolution (SWEEP-019):** each native composition now creates an OS-exclusive `batch-grid-<generation>.png` in the cache, encodes and synchronizes the PNG through that owned file handle, then retains and returns that immutable path. A stale writer therefore cannot mutate the accepted request's composite. No frontend changes were required for correctness because existing tokens already discard stale returned paths; deletion of superseded/orphaned generations remains intentionally deferred to RT-04's ownership-aware retention work rather than introducing a count-based prune that could delete an in-flight accepted path. Minimal implementation and regression file: `compose_grid.rs`. **Independent of FE-06/XC-06; coordinate later cleanup with RT-04.**

### RT-03 — Concurrent Values generations overwrite the artifact paths behind an accepted result (confirmed defect, P2)

- **Classification / evidence:** native cache race. `value_analysis.rs:116-128` keys the writable directory only by sanitized logical `image_id` plus level/mode; every source generation then overwrites `neutral.png`, `preview.png`, `bucket-map.png`, and `meta.json` in that directory (`164-171`, `242-282`). `value-analysis-runner.svelte.ts:100-129` starts a new native request after invalidating only frontend ownership; the older Rust computation continues. Export auto-analysis is a second caller.
- **Trigger / consequence:** scrub a reused video entry from frame A to B while A's Values computation is in flight (or overlap view/export requests). B may return an accepted result whose paths are subsequently overwritten by stale A. Frontend tokens reject A's result object but cannot stop its filesystem writes, so displayed/exported images can show A while statistics and selection identify B; interleaving can also mix the three PNGs and metadata.
- **Validation performed:** path derivation proves distinct source paths with the same logical ID/level/mode share all four writable targets; both caller and command are concurrently invocable and there is no generation, lock, temporary directory, or commit guard.
