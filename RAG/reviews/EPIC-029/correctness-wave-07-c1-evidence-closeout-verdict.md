## C1-H15 — binding evidence clarifications

1. **First callback absence is source-explained.** Wry0.55.1 initializes pending_scripts as Some, invokes Started from didCommit before draining it, queues only script bytes when eval is called inline, and drains with no completion handler. Therefore the first challenge's explicit JS receipts/activation may be real while its eval callback is absent. This explains all three incarnation observations; do not add arbitrary delay or treat callback absence as receipt. The underlying lines are wkwebview/mod.rs:569-594,720-775 and navigation.rs:17-35, with runtime-wry main-thread dispatch:235-249.
2. **Correct the hypothetical prefix, not the old report.** The report's predecessor-acquisition schedule needs A's renderer-side session to be absent: for example its initial bootstrap or guarded session grant is still held/lost. Actual challenge_job copies state.session.token into knownSession when present. If A already knows its N session, Started(B) retires it and that carried token is rejected as RetiredSession rather than activating N+1. With knownSession=None, an N+1 challenge hypothetically executed in predecessor A can still activate first; after B activates, a differing A nonce is rejected as ChallengeConsumed. Preserve this distinction. This is a source-unruled hypothetical delivery direction, not an observed WebKit bug.
3. **Keep the exact unresolved premise.** [Apple didCommit documentation](https://developer.apple.com/documentation/webkit/wknavigationdelegate/webview%28_%3Adidcommit%3A%29?language=objc) describes the main-frame content/update boundary. One finite successful run does not prove the pre-activation predecessor-exclusion premise. Conversely, missing public identity alone does not prove the platform actually misroutes such an eval.
4. **Manual creation is the selected attachment shape, not a proved unique API solution.** The candidate's existing setup body runs after configured windows and cannot retroactively install a pre-navigation captured identity there. Native state can also be prepared on Builder before build; this report did not prove every alternative builder/global attachment impossible. ## Lead-selected next design hypothesis

Inspect a **nonrenewable native WebView incarnation**: one authority-bearing document per native incarnation; no later Started, renderer retry or reload can mint a successor session inside that same WebView. A replacement document would require a newly created native WebView/incarnation, and old-incarnation work remains permanently rejected. Native registry/other owners must survive the renderer replacement; this is not permission to flush caches or delete owned data.

This is a read-only feasibility hypothesis, not a new accepted product behavior or permission to rebuild the running window. Prefer preserving the existing native OS window if the currently enabled public APIs support replacing its WebView; if only whole-window replacement, unsupported/private API, runtime patch or feature change is available, report that exact consequence. Initial about:blank/navigation and admission ordering must be accounted for, not assumed away.
