## 1. Native current-document premise

### What the exact chain establishes

On the locked macOS path, Wry registers `webView:didCommitNavigation:` and `webView:didFinishNavigation:` but no provisional-start handler at `wry-0.55.1/src/wkwebview/class/wry_navigation_delegate.rs:71-79`. Its `did_commit_navigation` receives both the webview and navigation, discards `_navigation`, and synchronously calls `on_page_load(PageLoadEvent::Started)` at `wry-0.55.1/src/wkwebview/navigation.rs:17-26`. The wrapper supplies a URL read from the retained webview rather than from the navigation at `wry-0.55.1/src/wkwebview/class/wry_navigation_delegate.rs:126-130`. Runtime Wry maps that event without adding identity at `tauri-runtime-wry-2.11.4/src/lib.rs:5029-5040`; Tauri's wrappers use current label-map lookup at `tauri-2.11.5/src/manager/webview.rs:288-311` and `tauri-2.11.5/src/webview/mod.rs:762-772`.

The harness adds application identity, not platform identity. It captures a native-issued incarnation in the builder-local initialization script and page-load closure at frozen H14 `src/driver.rs:1146-1179,1586-1612`. Only a captured-current `Started` calls `page_started`, creates a generation/challenge, and submits the challenge at `src/driver.rs:456-541`. The script accepts only the captured incarnation and a strictly larger generation at `src/driver.rs:1188-1266`. Source therefore proves that an older generation delivered into a later initialized page cannot lower the page slot. Run02 rows 154-157 directly observe that direction once.

It does not prove the inverse delivery direction away. `Webview::eval_with_callback` supplies only script/callback (`tauri-2.11.5/src/webview/mod.rs:1925-1939`); runtime dispatch is keyed by window/webview ID (`tauri-runtime-wry-2.11.4/src/lib.rs:1889-1903,3745-3752,3786-3791`); Wry calls `WKWebView.evaluateJavaScript` without the triggering `WKNavigation` or an expected document (`wry-0.55.1/src/wkwebview/mod.rs:720-775`). Apple's `didCommit` contract says content receipt has begun, but neither that contract nor these sources state that predecessor A's JavaScript realm is already unable to receive an eval submitted from `Started(B)`.

### Smallest still-unruled counterexample

1. A is current in webview incarnation I at generation N. Navigation B reaches `didCommit`; Wry emits `Started(B)`. Native state advances to N+1 and issues challenge C(N+1).
2. Before B's document-start state receives C, the uncorrelated `evaluateJavaScript(C)` executes in predecessor A. This is the exact behavior that source/contract do not expressly exclude; it was not observed in Run02.
3. A has the same incarnation I and page slot N, so the in-page monotone guard accepts N+1. A's bootstrap reaches native first and activates the N+1 session using A's document nonce. B's later bootstrap is rejected because the challenge/session is already consumed.

This is an untested hypothesis, not a claimed WebKit behavior. It is nevertheless the smallest counterexample the current evidence cannot rule out. If B has already activated first, the frozen state machine rejects a different-nonce A bootstrap as `ChallengeConsumed` (`src/protocol.rs:178-225`), so an obsolete page cannot replace an already-active native session in that narrower post-activation state. The remaining C1 obligation is precisely the pre-activation predecessor-execution interval above, not nonce entropy, label equality, or late-arrival ordering.

Run02 narrows but does not discharge that obligation. Rows 83-100 show B commit/activation followed by a deliberately later A-intended unguarded eval executing in B; rows 116-132 show the guarded analogue rejecting in B. Case 5's eight already-submitted eval/navigation trials reported zero page receipts within their finite 750 ms bounds (summary row 427), classified unknown/canceled/undelivered. No row proves a universal predecessor-terminal rule.

## 2. Initial callback discrepancy

The discrepancy is supported first-commit behavior in locked Wry, not an unexplained success condition:

1. Every new macOS Wry webview initializes `pending_scripts` to `Some(Vec::new())` and gives it to the navigation delegate (`wry-0.55.1/src/wkwebview/mod.rs:569-594`). Initialization scripts are installed before initial navigation (`:636-657`) as main-frame `WKUserScript` at document start (`:777-788`).
2. At initial `didCommit`, Wry calls the page-load handler first, then locks and drains `pending_scripts` (`wry-0.55.1/src/wkwebview/navigation.rs:17-35`).
3. Runtime Wry handles messages inline when already on its main thread (`tauri-runtime-wry-2.11.4/src/lib.rs:235-249`). The harness `Started` callback synchronously reaches `submit_eval` (`src/driver.rs:456-541,611-674`), so Wry sees `pending_scripts = Some`.
4. In that branch Wry pushes only `js.into()`; it does not retain the supplied callback (`wry-0.55.1/src/wkwebview/mod.rs:720-723`). Control returns to `didCommit`, which evaluates each queued string with completion handler `None`, then sets the queue to `None` (`wry-0.55.1/src/wkwebview/navigation.rs:28-35`). Later reload evals take the normal callback branch at `wry-0.55.1/src/wkwebview/mod.rs:724-775`.
5. The challenge script itself schedules `bootstrap` and sends `eval_report` over explicit IPC before returning its report (`frozen H14 src/driver.rs:1203-1253`). Those actions do not depend on the dropped `eval_with_callback` completion handler.

That explains exactly the Run02 triples 4 -> 7 -> 8, 435 -> 438 -> 439, and 460 -> 463 -> 464. Rows 5, 436, and 461 prove only Tauri/runtime dispatch acceptance. Rows 7, 438, and 463 are the explicit renderer-to-native execution receipts. Rows 8, 439, and 464 are native bootstrap validation/activation. The missing callbacks are neither counted as successful delivery nor needed as the harness authority receipt. Run01's matching 66/63 pattern is consistent with the same source path, but its failed terminal outcome remains a preserved shutdown counterexample, not a second passed experiment.

## 3. Exact production attachment delta

Only these existing attachment points have to differ from the manually built harness topology:

1. **Configured window:** candidate `tauri-app/src-tauri/tauri.conf.json:21-30` currently auto-creates the main window. Tauri builds every `create` window before invoking application `setup` (`tauri-2.11.5/src/app.rs:2520-2532`). The authority-carrying window therefore has to stop being auto-created and instead be constructed manually after native C1 state exists. Its present title/size/minimum/decorations are configuration to preserve, not evidence of identity.
2. **Managed native owner:** candidate `tauri-app/src-tauri/src/main.rs:58-90` currently manages only `EventLog` and `ProfileState` from setup; `tauri-app/src-tauri/src/lib.rs:1-8` merely exports `artifact_ownership`. A C1 adapter state must be installed before manual window construction and must own both the session/incarnation/generation table and the accepted 193-A `ArtifactRegistry`, so stale rejection occurs before any acquire/register/release mutation. This is the production attachment of 193-A, not a change to its retention model.
3. **Builder-local identity and document start:** unlike current `main.rs`, the manual builder must mint one incarnation before build, embed that fixed value in an initialization script installed before navigation, and capture the same value in the builder-local page-load closure. Frozen H14 `src/driver.rs:1146-1179,1586-1612` demonstrates the attachment shape. The native `Started` handler alone may advance generation; `Finished`, renderer nonce, request arrival, visibility, and retry may not.
4. **Lifecycle attachment:** current `main.rs:91-96` has only a global focus logger. Retirement/destruction handling for the authority-carrying window must reach the same managed adapter with the captured incarnation; a reusable label/public handle is not the identity. Frozen H14 `src/driver.rs:1613-1627` demonstrates the capture shape, while Run02's old lifecycle callbacks at rows 448-449 are explicitly injected and do not establish late platform delivery.
5. **Invoke boundary and renderer bootstrap:** current `main.rs:100-115` registers ordinary commands, and `src/lib/bridges/tauri.ts:17-85` resolves a generic invoke with no lifetime envelope. C1 bootstrap/challenge receipt and later authority-bearing calls must enter the same adapter; every 193-A-bearing command must be rejected there before registry mutation unless its validated session matches. The native builder's document-start script, not `src/main.ts:37-70` after parsing/mount preparation, is the initialization point. `App.svelte:214-227,257-300` visibility/focus/page events remain diagnostics only.

The attachment shape is source-feasible and was directly exercised by one manually built macOS harness. The initial Tauri attachment barrier remains source-open: native build/navigation begins before the returned webview is entered in Tauri's label map, so a sufficiently early initial callback could still be dropped; Run02 only observed that it was not dropped in its three incarnations. Actual late same-label platform callbacks, the predecessor-execution schedule above, production integration, and Windows/Linux behavior are also open. The pure protocol checks and forced ledger cases establish fail-closed application transitions only; they do not promote those platform premises.
